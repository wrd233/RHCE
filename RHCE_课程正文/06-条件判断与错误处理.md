# 条件判断与错误处理

when 不是为了把 Playbook 写成复杂程序，而是让“同一份自动化”能根据机器实际情况做正确的事情。

条件判断的触发点通常有三类：机器自身不同（facts）、用户输入不同（vars）、前一个任务结果不同（register）。内存阈值、CPU、OS、命令输出、配置变化这些场景——内存阈值、CPU、OS、命令输出、配置变化——都可以放进这三类。

### when 的第一条规则：变量直接写，不要再套 `{{ }}`

```
when: ansible_memfree_mb > 500
when: inventory_hostname == 'node1'
when: item.job == 'developer'
```

因为 when 本身就是一个表达式上下文。把变量再写成字符串插值不仅多余，在某些版本还会给 warning。

### 数字、字符串、逻辑运算：重点在数据类型

`> < >= <=` 做大小比较，`== !=` 比较相等，`and/or/not` 组合条件。例如我们想判断 RHEL 主版本至少为 8。这里补一个很实用的习惯：版本 fact 经常是字符串，如果你确实按整数版本判断，写成 `(ansible_distribution_major_version | int) >= 8` 更稳，避免字符串比较在两位数版本上产生直觉外结果。

### register + when：把返回结果当条件

你可以判断 `status.rc == 0`，也可以用结果测试：`status is succeeded`、`status is changed`、`status is failed`、`status is skipped`。不同资料可能把测试名称写成简写；实际可用名称请以当前 Ansible 文档为准。

### 文件属性测试：先确认“这个路径是在哪台机器上判断”

`file/directory/link/mount/exists` 这类 Jinja 路径测试判断的是控制端/模板执行上下文路径，不是受管节点路径。这一点特别容易误用。如果要判断远端文件是否存在，更推荐 `ansible.builtin.stat` 注册结果，或者执行一个远端探测 task 再 register。

### 变量测试与 in

`defined`/`undefined`/`none` 很适合“这个参数有没有提供”；`in` 很适合判断组名、设备名、列表成员，例如：

```
when: "'dev' in group_names"
when: "'vdb' in ansible_devices"
when: ansible_devices.vdb is defined
```

这就是模拟题第 11 题判断磁盘是否存在、模拟题第 13 题判断主机属于哪个组的核心。

### Jinja tests：lower / upper / even / odd / divisibleby / subset ...

还有一些性质测试：它们不是 RHCE 最核心的背诵点，但你要知道 when 并不只有比较运算符，还可以用“测试”描述类型或性质，例如 `var is string`、`num is even`。现场如果遇到陌生 test，不要硬背，优先从题目需要出发。

### block / rescue / always：这是存储题的关键模型

block 有两个作用。第一个是“把一组 task 当成一个逻辑单元”，可以在 block 层统一挂 `when`、`become` 等。第二个是错误处理：block 里出现失败，就进入 rescue；无论 block 最终成功还是经过 rescue，always 都会执行。

```
- block:
    - name: try 600 MiB
      lvol:
        vg: research
        lv: data
        size: 600m
  rescue:
    - debug:
        msg: Could not create logical volume of that size
    - name: fallback 400 MiB
      lvol:
        vg: research
        lv: data
        size: 400m
  always:
    - name: format final LV
      filesystem:
        fstype: ext4
        dev: /dev/research/data
```

把它当成异常处理就很好理解：**先尝试理想方案 → 失败时按题目要求降级 → 最后做共同收尾。**第 10/11 题之所以显得难，不是 LVM/分区本身难，而是这种控制流第一次出现。

**考试思维：**不要一上来写 YAML。先画分支：资源不存在怎么办？存在但容量不足怎么办？成功怎么办？最后必做什么？当流程图能说清，block/rescue/always 只是把流程翻译成语法。

### 第 10 题：先分清“卷组不存在”和“容量不够”

题目要在所有节点创建 `research/data`：先尝试 600 MiB，容量不足时显示指定消息并尝试 400 MiB；如果 `research` 卷组根本不存在，则只显示另一条消息。**这不是同一类失败。**我会先用 `ansible_lvm.vgs` 判断卷组存在与否；只在卷组存在的节点运行 `block/rescue`。格式化之前还要确认逻辑卷确实创建成功，绝不能让 `always` 无条件格式化一个不存在的设备。

```yaml
- name: Create the requested logical volume
  block:
    - name: Try 600 MiB
      community.general.lvol:
        vg: research
        lv: data
        size: 600m
  rescue:
    - ansible.builtin.debug:
        msg: Could not create logical volume of that size
    - name: Fall back to 400 MiB
      community.general.lvol:
        vg: research
        lv: data
        size: 400m
  when: "'research' in ansible_lvm.vgs"

- name: Explain the absent volume group
  ansible.builtin.debug:
    msg: Volume group does not exist
  when: "'research' not in ansible_lvm.vgs"
```

接下来用 `stat` 检查 `/dev/research/data`，存在时才用 `community.general.filesystem` 创建 ext4；题目明确说**不挂载**，所以不要再加 mount。`rescue` 会接住 block 中的任务失败，不会自动判断失败原因一定是容量不足，因此运行时还要读错误信息，确认回退符合题意。`community.general.lvol` 和 `community.general.filesystem` 所属集合要以当前执行环境的模块文档确认。实验中预先造卷组只是为了模拟题能练出不同分支，不属于第 10 题交付动作。

### 第 11 题：先选设备，再处理容量回退

这题优先 `/dev/vdd`；若它不存在，先输出 `disk /dev/vdd does not exist`，再考虑 `/dev/vdb`。我们从 `ansible_devices` 决定唯一的 `target_disk`，然后对它做分区、文件系统和挂载，避免两个磁盘同时尝试挂载到 `/mnt/fs01`。如果 1500 MiB 的分区因容量不足失败，`rescue` 再创建 800 MiB；分区起点、编号与结尾要匹配实际磁盘几何，不能把 `1501MiB` 当作到处通用的数。两个候选设备都不存在时，也应明确报告 vdb 缺失。

存储题的验收必须回到系统状态：`lsblk -f` 看设备、文件系统和挂载点，`findmnt /mnt/fs01` 看当前挂载，`/etc/fstab` 看重启后的持久性。实验材料里为腾出磁盘而执行的 `lvremove`、`vgremove`、`dd` 是重置练习环境的操作，不应放进题目 Playbook，也不应对真实数据盘照做。

### 当失败本身就是题意的一部分

`when` 决定“运行还是跳过”，`failed_when` 决定“什么结果算失败”，`fail` 模块可以主动终止并给出明确原因。比如某个检查命令的退出码为 0，却在输出中出现 `ERROR`，我们可以用 `failed_when: "'ERROR' in check.stdout"` 把它判成失败；反过来，若某种非零退出码在题意内可接受，也可以按条件调整失败判定。不要为了让界面变绿而直接加 `ignore_errors: true`，它会让真正的失败信息失去作用。

```yaml
- name: Inspect the service state
  ansible.builtin.command: systemctl is-active httpd
  register: service_check
  changed_when: false
  failed_when: false

- name: Explain the inactive state
  ansible.builtin.debug:
    msg: httpd is not active on this host
  when: service_check.rc != 0
```

这里检查任务本身不会改系统，`changed_when: false` 让输出更符合事实；`failed_when: false` 允许我们在下一步解释状态。若题目要求“服务必须运行”，就不能停在 debug，后续还要用 service 模块修复并再次检查。

### 先用简单判断练眼睛，再读复杂的 block

`when: ansible_os_family == 'RedHat'` 可以让一个包安装任务只在合适的系统执行；`when: ansible_memtotal_mb | int >= 512` 可以表达内存下限；`when: result.rc == 0` 可以看前一个命令是否成功。多个条件用 `and`、`or`、`not` 组合，遇到复杂表达式加括号让逻辑清楚。变量尚不存在时先用 `is defined`，值为空时再用 `is none`；这与“变量不存在”不是一回事。

另外，一些 Jinja tests 用来判断性质：`path is file/directory/link/mount/exists` 查看的是控制端路径；`text is lower/upper` 看大小写；`number is even/odd/divisibleby(3)` 看数值；`a is subset(b)`、`b is superset(a)` 看集合关系，`value in list` 看成员关系。第 10、11、13 题真正频繁用到的是 `in`、`is defined`、数值比较和注册结果；其他测试知道有这个工具箱，遇到题再查即可。

当题目要求明确中断并显示消息，我会用 `ansible.builtin.fail` 配合 `when`，例如关键变量缺失就让任务失败；当模块返回码不足以表达成功与否，用 `failed_when` 指定真正的失败条件。两者都属于“让失败语义诚实”，不要与 `rescue` 混为一谈：`rescue` 是前一步失败之后，题面允许的另一条完成路径。
